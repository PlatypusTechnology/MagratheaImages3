# Plan: UUID for images (v.3.5.0)

Guided implementation for `blueprint-uuid.md`. Split into 3 phases, one session each, in the
same order the blueprint itself suggests: database → other changes → reinforced UUID changes.
Each phase is a self-contained session: do the phase, verify it, stop. Don't start the next
phase in the same session unless explicitly asked.

Framework notes that shape this plan (from the vendored `magrathea-php2` skill, confirmed against
the vendored source in `src/vendor/platypustechnology/magratheaphp2`):
- `MagratheaModel` already has native `uuid` field support: declare
  `$this->dbValues["uuid"] = "uuid";` and a matching public property, and `Insert()` fills it via
  `Uuid::V7()` whenever it's left empty (never overwrites a pre-set value, never touches it on
  `Update()`). Confirmed present in the vendored `MagratheaModel.php` (lines ~231, ~450), so no
  framework upgrade is needed.
- The project's "AppConfiguration" (blueprint's term) is `ConfigApp` / the `_magrathea_config`
  table — read via `ConfigApp::Instance()->Get(...)` / `GetInt(...)`. This is distinct from
  `Config` (`magrathea.conf`).
- `src/version` (plain text, e.g. `3.4.2`) + `src/changelog.md` are bumped together as the last
  commit of a change (confirmed via `git log`/`git show` on the `v.3.4.1`/`v.3.4.2` commits).
  `src/configs/version.php` is CI-generated by `build.sh` — never hand-edit it.
- `swagger.yaml` (project root `src/swagger.yaml`) is hand-maintained alongside API changes
  (see commits "updating response and swagger", "swagger and skill updates") — update it in the
  same phase as the routes/behavior it documents.

## Decisions (settled)

Four open points were reviewed and closed before implementation:

1. **Generated image filenames — dual, on-demand, symmetric.** Each access style gets its own
   independent cache namespace, populated lazily exactly like today: an id-based request
   generates/reads `<id>_<size>.webp`, a uuid-based request generates/reads `<uuid>_<size>.webp`.
   Nothing is pre-generated for the style that wasn't requested. This keeps the id-based path's
   existing zero-DB `LookForImage()` fast path completely untouched, and gives uuid-based requests
   the same fast path once their own cache is warm. Delete cleanup must glob both patterns. See
   Phase 3 step 4 for the mechanism (`Images` needs to know, per-request, which identifier resolved
   it).
2. **`images.uuid` column — `NOT NULL` after backfill.** The migration adds it nullable, backfills
   every existing row, then `ALTER`s it to `NOT NULL` in the same script — enforced at the DB level,
   not just by convention.
3. **Backfill UUID version — v4 is fine.** `UPDATE images SET uuid = UUID() WHERE uuid IS NULL` (v4)
   for existing rows is acceptable; new rows get v7 via the framework's `Insert()`. Kept as plain
   SQL, no PHP backfill script needed.
4. **Dropping `secure_api` — remove the `"secure"` key entirely** from `/settings` and `/version`,
   no backward-compatible hardcoded value.

## Phase 1 — Database & migration (Session 1)

**Goal:** add a unique `uuid` column to `images`, generate it for existing rows, wire the model
to the framework's native `uuid` field type. No API/behavior changes yet — this phase only touches
schema and the model definition.

**Files:**
- `database/database.sql` — fresh-install schema
- `database/migrations/migration-3.5.0-image-uuid.sql` — new
- `src/api/features/Images/Base/ImagesBase.php` — generated model base

**Steps:**
1. In `database/database.sql`, add `uuid` right below `id` in the `images` table:
   ```sql
   CREATE TABLE `images` (
       `id` int(11) PRIMARY KEY AUTO_INCREMENT,
       `uuid` char(36) NOT NULL UNIQUE,
       `name` varchar(255) NULL,
       ...
   ```
2. Create `database/migrations/migration-3.5.0-image-uuid.sql`, following the shape of the
   existing `migration-3.3.0.sql`:
   ```sql
   -- Migration: Add `uuid` column to `images` table
   ALTER TABLE `images`
       ADD COLUMN `uuid` char(36) NULL UNIQUE AFTER `id`;

   -- Backfill existing rows (MySQL has no native UUIDv7; UUID() here is v4 —
   -- fine for a one-time backfill, new rows going forward get v7 via the model)
   UPDATE `images` SET `uuid` = UUID() WHERE `uuid` IS NULL;

   -- Enforce at the DB level now that every row has one
   ALTER TABLE `images`
       MODIFY COLUMN `uuid` char(36) NOT NULL;
   ```
3. In `ImagesBase.php`:
   - Add `uuid` to the constructor property list: `public $id, $uuid, $name, $filename, ...`
   - Add `$this->dbValues["uuid"] = "uuid";` in `MagratheaStart()`, right after the `id` line.
   - Leave everything else in the file untouched (it's the generated-base convention — don't add
     business logic here, that belongs in `Images.php`).

**Verify:**
- Run the migration against a dev DB copy; confirm every existing row gets a non-null, unique
  `uuid`.
- `new Images()` → set required fields → `Insert()` → confirm `uuid` is auto-populated with a
  v7-shaped value and `Update()` afterward doesn't change it.
- Fresh install from `database.sql` produces the same column.

**Out of scope for this phase:** no controller/API changes, no config, no `GetByUuid` lookup yet.
Don't touch `Images.php`, `ImagesControl.php`, or any route in this session.

## Phase 2 — "Other changes" section (Session 2)

**Goal:** the three independent cleanups the blueprint groups under "other changes." None of
these depend on the uuid column, so this phase can proceed even before Phase 3, matching the
blueprint's own ordering.

### 2a. Drop `secure_api`

Today it's read in 4 places (`grep`-confirmed, all outside vendor):
- `src/api/features/Images/ImagesApi.php:17` — `$this->isSecure = boolval(Config::Instance()->Get("secure_api"));`, then branched on inside `GetById()` (lines ~37-44)
- `src/api/api.php:60` — `"secure" => Config::Instance()->Get("secure_api")` in `/settings`
- `src/api/api.php:95` — `if(Config::Instance()->Get("secure_api")) { $this->SecureImages(); } else { $this->PublicImages(); }`
- `src/api/api.php:152` — `"secure" => Config::Instance()->Get("secure_api")` in `/version`

Steps:
1. In `ImagesApi.php`: delete the `$isSecure` property and its assignment in the constructor.
   In `GetById()`, always require and validate `public_key` (i.e. keep only the body of today's
   `if($this->isSecure) { ... }` block, unconditionally).
2. In `api.php`'s `AddImages()`: delete the `if/else` and the whole `PublicImages()` method
   (lines ~103-112) — those are exactly "the endpoints that would not work with `secure_api` off."
   Keep `SecureImages()`'s routes as the only image-viewing routes (you can inline it or rename it
   now that it's the only variant — your call, no behavior change either way).
3. Remove the `"secure" => ...` key entirely from both the `/settings` and `/version` response
   payloads in `api.php` — no backward-compatible hardcoded value. This is a breaking response-shape
   change for any consumer reading `settings.secure`, accepted as part of this change.
4. Remove `secure_api` from `src/configs/magrathea.conf` and `src/configs/magrathea.conf.sample`
   (both `[dev]` and `[production]` sections in each file).
5. Update `src/swagger.yaml`: drop the `images-public` tag and any `/image/:id/...` (no-key)
   paths, keep only the `/image/:key/:id/...` shapes, and remove the `secure_api` mention from
   `info.description`.

### 2b. Dynamic key sizes

Today, `ApikeyControl::createKey()` (`src/api/features/Apikey/ApikeyControl.php:24-26`):
```php
public function createKey(bool $private, int $tries=0): string {
    $length = $private ? 25 : 12;
```
Change to read optional sizes from `ConfigApp` (the `_magrathea_config`-backed config, not
`magrathea.conf`), falling back to the current hardcoded defaults:
```php
$length = $private
    ? ConfigApp::Instance()->GetInt("private_key_size", 25)
    : ConfigApp::Instance()->GetInt("public_key_size", 12);
```
Add the `use Magrathea2\ConfigApp;` import. Nothing else in the codebase assumes a fixed
25/12-char key length (confirmed by `grep` — `assertKeyNotInUse()`/`createRandomStr()` are already
length-parameterized, and the only place `25`/`12` are hardcoded literals is this one spot), so
keys of a different configured size work the same everywhere else once created. Verify by:
- Setting `private_key_size`/`public_key_size` via the AppConfig admin feature to something other
  than 25/12, creating a key, and confirming upload/view/delete all still work with the
  different-length key.
- Confirming key creation still works with neither value set (falls back to 25/12 exactly as today).

### 2c. `/changelog` endpoint

The example function in the blueprint calls `$this->Cache("changelog")` — the
peek-cache-by-name pattern from `MagratheaApiControl::Cache($name, $data=null)`. That means it
belongs on a class extending `MagratheaApiControl`, not as a bare closure inside `api.php`'s
`MagratheaImagesApi` (which extends `MagratheaApi`, whose own `Cache($data)` has a different,
incompatible signature/purpose — it caches a full response payload, not a peek-by-key). Don't try
to wedge this into the existing closure-style routes in `GeneralApis()`.

Steps:
1. Create `src/api/shared/SystemApi.php`:
   ```php
   <?php
   namespace MagratheaImages3;

   use Magrathea2\MagratheaApiControl;
   use Magrathea2\MagratheaHelper;
   use Magrathea2\MagratheaPHP;

   class SystemApi extends MagratheaApiControl {
       public function GetChangelog(): array {
           $this->Cache("changelog");
           $filepath = MagratheaHelper::EnsureTrailingSlash(MagratheaPHP::Instance()->magRoot)."changelog.md";
           if (!file_exists($filepath)) return [];
           $content = file_get_contents($filepath);
           $lines = preg_split('/\r?\n/', $content);
           $changelog = [];
           $current = null;
           foreach ($lines as $line) {
               $line = trim($line);
               if (preg_match('/^## v\.([0-9.]+)/i', $line, $m) || preg_match('/^## ([0-9.]+)/i', $line, $m)) {
                   if ($current) $changelog[] = $current;
                   $current = ['version' => $m[1], 'date' => null, 'changes' => []];
               } elseif (preg_match('/^([0-9]{4}-[0-9]{2}-[0-9]{2})/', $line, $m)) {
                   if ($current) $current['date'] = $m[1];
               } elseif (preg_match('/^- \*\*(new|fix|improvement|improvements)\*\*:? (.+)$/i', $line, $m)) {
                   if ($current) $current['changes'][] = ['type' => strtolower($m[1]), 'description' => $m[2]];
               }
           }
           if ($current) $changelog[] = $current;
           return array_slice($changelog, 0, 5);
       }
   }
   ```
   Note the two tweaks vs. the blueprint's example, both required to actually match this repo's
   real `src/changelog.md` (checked against its current content):
   - This project's version headers are `## 3.4.2` (no `v.` prefix), and the date line is
     `2026-08-01` with no `###` — the blueprint's example regexes (`^## v\.` and `^### `) were
     copied from a different API's changelog format and wouldn't match here at all. The version
     shown above matches both `## 3.4.2` and (if ever written that way) `## v.3.4.2`.
   - Added `improvements` (plural) as a recognized type, since `changelog.md` already uses
     `**improvements**` (see the `3.4.1` entry) alongside singular `**improvement**`.
2. Register the folder and the route:
   - In `src/api/_inc.php`, add `"shared"` to the existing `AddCodeFolder(...)` call (it's
     currently only pulled in via a manual `include("shared/Helper.php")`, which won't autoload a
     new class in that folder).
   - In `src/api/api.php`'s `GeneralApis()`, add:
     `$this->Add("GET", "changelog", new \MagratheaImages3\SystemApi(), "GetChangelog", self::OPEN);`
3. Add a `changelog` path to `src/swagger.yaml` under the `system` tag.

**Verify (Phase 2 overall):**
- `/settings` and `/version` no longer return `secure`; no route responds at the old bare
  `/image/:id/...` paths (404 instead).
- New key creation honors configured `private_key_size`/`public_key_size` and falls back
  correctly when unset.
- `GET /changelog` returns the 5 most recent parsed entries from `src/changelog.md`, and a second
  call within the cache window is served from cache (check via `MagratheaCache` behavior / a log
  line, not just response equality).

## Phase 3 — Reinforced UUID changes (Session 3)

**Goal:** the config flag, the dual id/uuid lookup on every image-viewing endpoint, and the
dual-namespace generated-filename scheme (see Decision 1 above). Depends on Phase 1 (column +
model) and Phase 2 (secure_api already dropped, so every image route already carries
`:public_key`).

**Files:**
- `src/configs/magrathea.conf`, `magrathea.conf.sample` — new `force_uuid` key
- `src/api/features/Images/Images.php` — `BuildGenFileName()`
- `src/api/features/Images/ImagesApi.php` — `GetById()`, `LookForImage()`
- `src/api/features/Images/ImagesControl.php` (or `Base/ImagesControlBase.php` query) — uuid lookup
- `src/api/features/Images/ImagesControl.php` — `RemoveRawFile()` generated-file cleanup pattern
- `src/swagger.yaml`
- `src/changelog.md`, `src/version` — version bump, done last

**Steps:**
1. **Config:** add `force_uuid = false` next to `webp_quick_access` in both `[dev]` and
   `[production]` sections of `magrathea.conf` and `magrathea.conf.sample`.
2. **Lookup by uuid:** add a control method mirroring `ApikeyControl::GetByKey()`'s style, e.g. in
   `ImagesControl.php`:
   ```php
   public function GetByUuid(string $uuid): ?Images {
       $q = Query::Select()->Obj(new Images())->Where(["uuid" => $uuid]);
       return $this->RunRow($q);
   }
   ```
3. **Route param detection in `ImagesApi::GetById()`:** the URL segment (today always `:id`) can
   now hold either a numeric id or a uuid string. Add a small helper, e.g.:
   ```php
   private function ResolveImage($idOrUuid): ?Images {
       $forceUuid = boolval(Config::Instance()->Get("force_uuid"));
       $looksLikeUuid = (bool) preg_match('/^[0-9a-f-]{36}$/i', $idOrUuid);
       if ($forceUuid && !$looksLikeUuid) {
           throw new MagratheaApiException("Images must be requested by UUID", true, 400);
       }
       $image = $looksLikeUuid ? $this->service->GetByUuid($idOrUuid) : new Images($idOrUuid);
       // accessId drives BuildGenFileName() (step 4) — records which identifier this
       // particular request resolved through, so the generated-file cache key matches
       // whichever style LookForImage() already used for its own fast-path lookup.
       if ($image) $image->accessId = $looksLikeUuid ? $image->uuid : (string) $image->id;
       return $image;
   }
   ```
   and call it from `GetById()` instead of `new Images($id)` directly. Keep the existing
   `empty($img->name)` "not found" check and the public-key/upload-key ownership check exactly
   as they are today — those don't change.
4. **Generated filenames — dual, on-demand, symmetric (Decision 1):** `BuildGenFileName()` needs
   to know, per-request, which identifier resolved the image, so it can key the filename the same
   way `LookForImage()`'s fast path will. Add a transient (non-persisted) property to `Images` and
   use it in `BuildGenFileName()` — `accessId` is set by `ResolveImage()` above, in step 3:
   ```php
   // Images.php
   public ?string $accessId = null; // set per-request by ImagesApi::ResolveImage(); not a DB field

   public function BuildGenFileName(string $addon): string {
       return ($this->accessId ?? $this->id)."_".$addon;
   }
   ```
   Nothing else in `GetThumbFile()`/`GetFileName()` needs to change — they already just call
   `BuildGenFileName()`.
5. **Delete-time cleanup:** `ImagesControl::RemoveRawFile()` currently globs `$img->id."_*"` for
   generated files. Since both an id-named and a uuid-named cache namespace can now exist for the
   same image (whichever were actually requested), glob both patterns on delete:
   ```php
   "del_generated" => array_merge(
       $manager->DeleteGeneratedPattern($img->id."_*"),
       $manager->DeleteGeneratedPattern($img->uuid."_*"),
   ),
   ```
   (`DeleteGeneratedPattern()` already tolerates a pattern matching zero files — it's a `glob`-style
   shell pattern, not a strict existence check — so this is safe even when only one namespace was
   ever populated.)
6. **Quick-access fast path:** `ImagesApi::LookForImage($params, $size)` builds
   `$id."_".$size` straight from `$params["id"]` before any DB hit — this stays exactly as it is
   today, unchanged. Because filenames are now keyed by whichever identifier is actually in the URL
   (id or uuid, symmetrically — Decision 1), the existing zero-DB logic already produces the right
   cache key for either access style with no modification needed; no id/uuid detection has to happen
   in this fast path at all.
7. **Swagger:** update `src/swagger.yaml` — the `:id` path param description should note it
   accepts either a numeric id or a uuid, note the `force_uuid` behavior (400 on id-based access
   when enabled), and bump `info.version` to `3.5.0`.
8. **Version + changelog (do this last, once 1-3 are all verified working together):**
   - Set `src/version` to `3.5.0`.
   - Add a `## 3.5.0` section to the top of `src/changelog.md`, e.g.:
     ```markdown
     ## 3.5.0
     2026-08-XX
     - **new:** images now have a UUID; existing endpoints accept either the numeric id or the UUID
     - **new:** `force_uuid` config flag to require UUID-only access
     - **new:** `changelog` endpoint
     - **improvement:** `private_key`/`public_key` sizes are now configurable via `private_key_size`/`public_key_size`
     - **fix:** removed `secure_api` — all image endpoints now always require the public key
     ```
     (fill in the real date when you actually cut this.)

**Verify:**
- With `force_uuid = false`: an image is reachable via both its numeric id and its uuid, at the
  same `/image/:public_key/:id-or-uuid/...` routes. Requesting a size via id produces/serves
  `<id>_<size>.webp`; requesting the same size via uuid produces/serves `<uuid>_<size>.webp` as a
  separate file — confirm both can exist side by side, and that a cache hit on either one truly
  skips the DB (e.g. temporarily break the DB connection and confirm a warm cache still serves).
- Deleting the image removes generated files under *both* naming patterns, no orphans left either
  way, regardless of which access styles were ever actually used for that image.
- With `force_uuid = true`: requesting via numeric id returns the "must be requested by UUID"
  error; requesting via uuid still works normally.
- `/settings`/`/version` (from Phase 2) still behave; nothing in Phase 1/2 regresses.
